# MacLink 1.3.2 developer notes

MacLink provides a macOS menu bar Connector and a Korean/English browser client. The public origin is `https://www.maclink.cloud`. The Connector opens outbound connections; it does not expose an inbound control listener.

## Components

| Path | Responsibility |
| --- | --- |
| `MacLink_Connector/` | Canonical AppKit menu bar UI, owned worker, screen capture, input and local settings |
| `MackLink_Web/connector/` | Published copy generated by `python3 scripts/sync-connector.py` |
| `MackLink_Web/app/page.tsx` | Google sign-in, device enrollment, key import and invitations |
| `MackLink_Web/components/remote-viewer.tsx` | WebRTC video/data channel, input mapping and reconnection |
| `MackLink_Web/lib/server.ts`, `lib/google-auth.ts`, `lib/turn.ts` | Authorization, signaling, server sessions and encrypted TURN settings |
| `MackLink_Web/lib/quality.ts`, `MacLink_Connector/quality.py` | Shared width, FPS and encoder bitrate targets |
| `MackLink_Web/db/`, `MackLink_Web/drizzle/` | D1 schema and ordered migrations |
| `scripts/build-macos-app.sh` | Self-contained app, deployment-target checks, signatures and DMG packaging |
| `MackLink_Web/app/privacy/`, `app/terms/`, `lib/legal-content.ts` | Public Korean/English policies |

Paths in the last column that start with `lib/` or `app/` are relative to `MackLink_Web/`.

## Authentication and credentials

Owners sign in with Google OpenID Connect, using state, nonce, PKCE and an opaque HttpOnly application session. Configure `GOOGLE_CLIENT_ID`, secret `GOOGLE_CLIENT_SECRET`, and `AUTH_BASE_URL=https://www.maclink.cloud` before activating this source. Preserve the existing secret `TURN_CONFIG_KEY`; never place credentials in source, logs or client bundles. See [Google setup](GOOGLE_LOGIN_SETUP.ko.md).

Google subject identifiers own devices. Equal email addresses never automatically merge accounts. A signed-in owner can explicitly import one legacy device with its existing connection-key JSON. The atomic claim checks the key and current ownership, revokes that device's old invitations/sessions and keeps its Connector key. Other devices and TURN settings remain with the previous account. A device already owned by another Google account cannot be claimed.

Guest access requires a valid invitation and the host's sign-in email, checked with a per-invitation attempt limit. Email matching identifies the intended host; it does not authenticate the guest. Persistent links permit repeated access without a new approval until revoked. Single-use links expire after one hour and normally require host approval.

## Media and input

Screen video and remote input use WebRTC exclusively. Automatic mode tries direct/configured TURN candidates and can retry with browser-side TURN/TLS 443. If both fail, it ends with an actionable network error. The Connector currently uses STUN; both sides blocking outbound UDP can still prevent connectivity even with browser-side TURN.

The website has no frame upload/download, remote input queue or HTTPS media transport. Ordinary HTTPS remains necessary for login, metadata, authorization and SDP/ICE signaling. TURN relays encrypted WebRTC packets; it does not decrypt media or the data channel. Data channels still enforce native event validation, sequence checks, view-only scope and macOS permissions.

The last decoded frame is retained only in bounded browser memory during recovery. It is revealed/replaced based on actual decoded frames. Input releases on focus loss, transport loss, permission pause or session replacement. The browser's timer fallback for browsers without `requestVideoFrameCallback` is still required and is unrelated to a network relay.

## Permission polling and recovery

The Connector starts status checks every four seconds, including time spent waiting for the prior response. A poll has a six-second timeout; mutations retain their normal timeout and are not automatically retried. Outages back off to at most ten seconds.

Without fresh authorization for 17 seconds, the Connector pauses capture and input. It can retain the existing peer for up to 30 seconds, then closes it. Local macOS permission revocation closes it immediately. Only a fresh active session with the same attachment and generation resumes the retained peer. Late closes, captures and SDP answers cannot mutate a replacement attachment.

Guest metadata polling, device online thresholds and server session leases remain necessary. Data-channel pings never extend the authorization lease. Diagnostic reports allow only states/counters and omit SDP, ICE addresses, credentials, screen contents and keystrokes.

## Quality targets

| Profile | Maximum width | Target FPS | Target / maximum encoder rate |
| --- | --- | --- | --- |
| low | 1600 px | 15 | 2 / 4 Mbps |
| balanced | 1600 px | 24 | 4 / 8 Mbps |
| high | 2560 px | 30 | 8 / 16 Mbps |
| ultra | 2560 px | 60 | 16 / 40 Mbps |

Preserve source aspect ratio without upscaling. Odd dimensions can round down for codec alignment. These are settings, not measured throughput or guarantees. Negotiated codecs, congestion control, host performance and network conditions affect actual results. A current encoder acknowledgment marks a profile applied.

## Storage and migration

D1 stores account/session metadata, device keys as hashes, invitations, signaling and encrypted TURN configuration. The active app requires `DB`; it no longer needs an R2 binding. Migration `0006_remove_https_relay.sql` removes the retired input table and session transport discriminator. Keep historical migrations unchanged so existing databases can advance in order.

Before activating the new production release, end old sessions and remove any legacy `frames/` objects in the previous R2 bucket through the hosting administrator's storage controls. Removing an R2 binding or a SQL table does not itself delete old R2 objects. The old public deployment must remain on its existing bindings until it is replaced. Preserve device registrations, authentication data and TURN settings.

Policies in this source describe the new WebRTC-only build. Do not publish those policies over a production build that still accepts screen/input uploads. Provider-specific processing countries and backup/log retention require final confirmation from the hosting agreement.

## Build and verification

Use Node.js 22.13+ and pnpm 11.25.0 for the website, with deployment-specific `.openai/hosting.json` containing the existing project ID and `d1: DB`. Google configuration is server-only.

```bash
cd MackLink_Web
pnpm install --frozen-lockfile
node --experimental-strip-types --experimental-sqlite --test tests/*.test.mjs
pnpm exec tsc --noEmit
pnpm build
```

Build the Connector on macOS with a macOS 13-compatible Python 3.11–3.14. The app includes Python. The default build performs a non-connecting executable self-test; use `--no-self-test` when no invocation of the built executable is allowed. Static Mach-O and signature checks still run.

```bash
python3 scripts/sync-connector.py --check
bash scripts/build-macos-app.sh --no-self-test
.build/maclink/venv/bin/python -m unittest discover -s MackLink_Web/tests -p 'test_*.py'
hdiutil verify dist/MacLink-Connector-arm64.dmg
```

Stop an installed Connector before replacing its bundle. Back up the previous app, retain the private key/configuration, verify version and executable bytes, and do not launch it when installation-only was requested. A same-version ad-hoc rebuild can require renewed macOS permission registration on its next launch. Installation alone does not prove a remote session works.
